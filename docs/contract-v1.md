# Контракт steer, схема 1

Всё, что пересекает шов между управляющей программой ([splify2](https://github.com/xyzmean/splify2))
и движком. Формат — **JSON**: он уже разбирается всем, что есть в базовом OpenWrt
(`jsonfilter`, blobmsg), LuCI говорит на нём нативно, и массивы сохраняют порядок — а
порядок каналов у нас семантически значим.

YAML сознательно не берётся: парсера в базовой системе нет (это ~100 КБ overlay на
коробке, где их шесть), а его неоднозначность (`no` → false, `1.10` → число) для
конфига, из которого генерируются правила фаервола, превращает опечатку в тихо другое
поведение. На роутер попадает JSON — и это не «пока»: конвертера из YAML нет и не
планируется, потому что он был бы вторым местом, где живёт представление о спеке.

Незнакомые ключи движок **молча пропускает**. Так управляющий слой может писать поля,
которых движок ещё не знает, не ломая apply — но это же означает, что опечатка в имени
ключа не будет замечена. Отказ на незнакомый ключ обменял бы один класс ошибок на другой,
худший: спека, написанная новым splify2, перестала бы применяться старым steer.

## 1. Спецификация (вход)

```json
{
  "schema": 1,
  "lan_device": "br-lan",
  "from_default": ["192.168.1.0/24"],
  "outputs": {
    "vpn":    { "kind": "interface", "devices": ["awg0", "wg0"], "on_fail": "drop" },
    "geo":    { "kind": "interface", "device": "debug" },
    "vl":     { "kind": "vless", "sub_file": "/etc/steer/sub.txt", "on_fail": "zapret" },
    "direct": { "kind": "direct" }
  },
  "channels": [
    { "name": "geoblock", "match": { "domains_files": ["/etc/steer/lists/geo.lst"] }, "out": "geo" },
    { "name": "blocked",  "match": { "prefixes_files": ["/etc/steer/lists/ipsum.lst"] }, "out": "vpn" },
    { "name": "tv",       "from": ["192.168.1.50"], "match": { "any": true, "allow_all": true }, "out": "vl" }
  ]
}
```

Канал матчит либо префиксы, либо домены — не оба сразу:

```json
{ "name": "geoblock", "match": { "domains_files": ["…/youtube.lst", "…/google.lst"] }, "out": "geo" }
```

Списков может быть **несколько на один канал**. Включить «youtube» и «google» в один
туннель не должно стоить двух каналов с двумя правилами и двумя наборами — с точки зрения
маршрутизации это одно направление. Именно списками, а не склеенным заранее файлом: на
коробке с 6 МБ overlay дублировать байты списков, чтобы выразить «и», — расход без отдачи.

Единственное число (`prefixes_file`, `domains_file`) тоже принимается: так писались первые
спеки, и ломать их значило бы заставить управляющий слой знать версию движка.

Доменный канал получает такой же набор в nft, но заполняет его не файл, а резолвер
(`steer dnsd`): на каждый домен выдаётся адрес из `198.18.0.0/15`, и в набор попадает
он, а не настоящий. Это и есть смысл затеи — два сайта за одним адресом CDN перестают
быть для роутера одним и тем же. Обратный перевод делает карта `fakeip` и цепочка
DNAT, которые генератор создаёт только если доменный канал вообще есть.

### Два режима доменного канала

```json
{ "name": "geo", "match": { "domains_file": "…/geo.lst", "mode": "realip" }, "out": "geo" }
```

- **`fakeip`** (по умолчанию) — каждому домену свой адрес из `198.18.0.0/15`. Точность
  по домену: два сайта за одним адресом CDN перестают быть одним и тем же.
- **`realip`** — в набор кладутся настоящие адреса из ответа, ответ уходит клиенту
  нетронутым. DNAT не участвует.

Выбор не косметический. При `fakeip` **traceroute показывает fake-адрес на каждом
хопе, включая первый**: получая ICMP-ошибку, ядро переписывает её внешний адрес
источника на тот, к которому обращался клиент, иначе клиент её не признает своей. Так
ведут себя все fake-IP реализации, не только эта. При `realip` хопы настоящие, но
точность теряется там, где два домена делят один адрес — и если они в разных каналах,
за оба решает тот, кто разрешился первым.

Показать промежуточные хопы при `fakeip` **нельзя** — проверено, а не выведено. Если
вывести ICMP-ошибки из-под conntrack (`notrack` на time-exceeded), ядро перестаёт
переписывать их адрес, но вместе с этим теряется единственный механизм, которым ошибка
попадает к клиенту: при masquerade она адресована роутеру, и связать её с клиентом
умеет только conntrack. Замер на живом клиенте: 13 ошибок поймано правилом, 0 дошло до
accept, все хопы после первого стали звёздочками. Отслеживание — это и есть доставка, а
отслеживаемость — это и есть переписывание. Третьего пути нет без правки вложенного в
ICMP заголовка с пересчётом контрольных сумм.

Опция `traceroute_hops` оставлена для случая **без NAT** на выходе (туннель несёт адреса
локальной сети как есть) — там ошибка адресована клиенту и всё работает. При
masquerade `apply` прямо говорит, что толку не будет.

Поэтому режим — свойство канала: у списка вроде `youtube` или `google` адреса
выделенные, и `realip` там ничего не стоит, а для общих CDN нужен `fakeip`.

`lan_device` нужен там же: редирект DNS обязан ловить и IPv6 (роутер по умолчанию
объявляет себя IPv6-резолвером, и клиенты предпочитают именно его), а стабильного
`ip6 saddr` у локальной сети нет — префикс динамический. Поэтому правило матчит
устройство.

`from_default` можно не указывать: тогда движок берёт IPv4-подсеть `lan_device`.
Отсутствие и того и другого раньше означало спеку без редиректа DNS вовсе — симптом
«с роутера работает, с устройств нет».

### Выход: список устройств и режим отказа

```json
"vpn": { "kind": "interface", "devices": ["awg0", "wg0"], "on_fail": "drop" }
```

`devices` — **приоритет**, ровно как порядок каналов: первое здоровое побеждает.
Восстановление наверх происходит само, отдельного механизма для него нет — как только
основной туннель ожил, он снова оказывается первым здоровым. `device` (единственное
число) — то же самое для одного устройства и одновременно поле, которое `failover`
переписывает: активное устройство отдельно от списка кандидатов, потому что менять
активное — не то же, что менять настройку.

`on_fail` отвечает на «куда трафик, когда не работает ни одно устройство»:

| | |
|---|---|
| `drop` (умолчание) | blackhole-маршрут |
| `direct` | открытым путём |
| `zapret` | то же, что `direct`, но с проверкой, что обход DPI запущен |

Умолчание `drop` выбрано против интуиции сознательно: канал заводят именно для того,
чтобы трафик **не** шёл напрямую, и молча вернуть его на открытый путь в момент поломки —
значит нарушить единственное обещание выхода тогда, когда это опаснее всего. Пусть лучше
не работает заметно, чем работает не туда незаметно.

Именно **blackhole**, а не пустая таблица: пустая таблица означает «ищи дальше», то есть
трафик утекает открытым путём вопреки настройке. Разница между «нет маршрута» и
«запрещённый маршрут» здесь и есть разница между работающим `drop` и его видимостью.

`zapret` без запущенного zapret — это `direct` под другим именем, поэтому проверка есть, и
она предупреждает, а не отказывает: обход DPI мог быть остановлен уже после apply.

`kind: vless` — [отдельный документ](vless.md). Для контракта важно одно: это выход **с
устройством**, и всё, что сказано про метки, таблицы и failover, применимо к нему без
изменений. Отличие только в том, что устройство надо создать, поэтому у него есть
`sub_file` (путь, не URL — скачивание делает управляющий слой) и `node` (номер узла;
`-1` по умолчанию означает «первый рабочий», и выбор делает проверка, а не человек).

### Склейка: один выход — максимум два набора

Каналы, совпадающие по выходу, набору клиентов и режиму, компилируются в **одну группу**:
один набор nft и одно правило. Их списки складываются.

Отсюда потолок: на выход приходится не больше двух наборов — адресный и доменный. На 4C
каждый набор — это отдельный проход по правилам на каждый пакет и отдельная его память,
поэтому «10 включённых категорий» не должны превращаться в 10 наборов.

Это меняет `status`: он отдаёт **группы**, а не каналы из спеки, и у каждой перечислены
входящие в неё каналы. Счётчики нельзя разложить обратно по каналам — правило одно, и
ядро считает его целиком. Ложная точность здесь была бы хуже отсутствия цифры.

### Защита от конфигураций, отрезающих доступ к роутеру

Всё ниже компилируется и применяется без единой жалобы, а замечается как «роутер
пропал». Отказать дешевле, чем объяснять, как чинить коробку, до которой уже не
достучаться.

- **выход в `lan_device`** — петля: помеченный пакет получает маршрут обратно в ту сеть,
  откуда пришёл;
- **устройство дважды в одном выходе** — делает failover бессмысленным: второй кандидат
  ничем не отличается от первого;
- **канал `any` без списков** требует явного `"allow_all": true`. Он уводит в туннель
  весь трафик клиента, включая доступ к самому роутеру и его DNS. Конфигурация законная,
  но без явного признака это почти всегда описка вместо списка;
- **пустая спека принимается.** Это не защита, а её отсутствие там, где она мешала:
  канал требует выхода, выход без каналов отвергался — и первичная настройка становилась
  невозможной. Проверка, из-за которой нельзя сделать первый шаг, защищает не того.

### Инварианты

1. **Порядок каналов — это приоритет.** Первое совпадение выигрывает. Генератор ставит
   правила в этом же порядке, и каждое заканчивается `return`, а не `accept`: `return`
   выходит из **нашей** цепочки, поэтому следующая группа пакет уже не увидит и не
   переразметит, а остальной фаервол продолжает работать как обычно. `accept` завершил бы
   весь хук и вырезал бы правила fw4, стоящие после.
2. **`match` содержит только пути к файлам.** Никаких встроенных списков — см. правило
   про слабое железо в README. Файл читает движок, напрямую в набор. Файлов может быть
   несколько на канал, и они складываются.
3. **Выход именованный, девайс подменяемый.** `outputs.vpn.device` меняется управляющей
   программой (это failover), и каналы при этом не трогаются. Смена девайса не должна
   требовать пересборки правил — только перепривязки таблицы.
4. **Метки и таблицы движок распределяет сам** и хранит в постоянном реестре: спека их
   никогда не называет. Реестр обязателен — иначе после перезагрузки метки
   перетасуются, а рядом живут mwan3 и fw4 со своими.
5. **Семейство — свойство канала**, а не глобальная настройка: иначе поддержка IPv6 стала
   бы переписыванием, а не доработкой. Это решение о форме, а не реализованная функция —
   поля `family` парсер пока не знает, всё компилируется как IPv4.
6. **Незнакомая `schema` — отказ, а не догадка.** Мажор ломает совместимость явно.
7. **Каждое сгенерированное правило несёт имя группы** в комментарии nft. Без этого
   невозможны ни `explain`, ни счётчики, а отладка на роутере без инструментов
   становится дороже самой поломки.
8. **Метка ставится до решения о маршруте.** Цепочка сидит на `priority mangle + 1`:
   раньше — и её обошёл бы mangle, позже — и маршрут уже выбран, метка ни на что не влияет.
9. **Правила живут в своей таблице** `inet steer`, а не включением в fw4. Поэтому
   `fw4 reload` их не сносит, а `/etc/init.d/steer stop` не может испортить чужой
   фаервол.

## 2. Состояние (выход)

`steer status` — то, что есть сейчас:

```json
{
  "schema": 1,
  "outputs": {
    "vpn": { "kind": "interface", "device": "awg0", "up": true,
             "mark": "0x00100000", "table": 300,
             "in_firewall": true, "nat": true,
             "devices": ["awg0", "wg0"], "on_fail": "drop" },
    "direct": { "kind": "direct" }
  },
  "channels": [
    { "name": "vpn_dom", "out": "vpn", "kind": "domains",  "live": true,
      "packets": 5009, "bytes": 1799237, "lists": 2, "channels": ["youtube", "google"] },
    { "name": "vpn_ip",  "out": "vpn", "kind": "prefixes", "live": true,
      "packets": 4, "bytes": 418, "lists": 1, "channels": ["blocked"] }
  ]
}
```

Три вещи, которые важно читать правильно:

- **`channels` — это группы, а не каналы спеки.** Имя (`vpn_dom`) сгенерировано, а состав
  перечислен в поле `channels`. Три канала спеки выше дали две группы. Раскладывать
  счётчики обратно по каналам нельзя: правило одно, ядро считает его целиком, и ложная
  точность была бы хуже отсутствия цифры.
- **`live: false` означает «правила такого нет в ядре»**, а не «нет трафика». Это разные
  вещи: первое — рассогласование применённого и живого, второе — просто тишина. Пока нет
  `steer verify`, это единственный признак, по которому его видно.
- **`in_firewall` и `nat`** — про то, что steer не контролирует. Туннель, не упомянутый ни
  в одной зоне, маршрутизируется правильно и молча не работает. Это чаще всего и есть
  ответ на «настроил, но не пускает».

Чего в `status` нет: `generation`, `applied_at`, предупреждений о состоянии списков. Первые
два требуют записывать применённое на диск, а не выводить из спеки; предупреждения о
списках отдаёт фиттер в своём отчёте, потому что резал он.

### Отчёт фиттера

```json
{"source":30726,"kept":19122,"waste_addresses":580000,"level":24,"min_count":2,
 "malformed":0,"truncated":true,"fits":false,"punched":0,"covered_through":"198.38.96.0"}
```

`covered_through` — обязательное поле при `truncated`. Сообщать «оставлено 19 122 из
30 726» бесполезно: человек видит, что часть сайтов работает, а часть нет, и не может
связать это с памятью. Пример из жизни: у youtube.com десятки A-записей, и на обрезанном
списке `142.250.130.190` уходил в туннель, а `216.58.198.206` — напрямую, потому что
отсечка легла на `198.38`. Симптом выглядел как «пару часов назад работало».

**Отсюда порядок действий фиттера:** сначала агрессивнее сливать префиксы, сохраняя полное
покрытие (лишний адрес в туннеле почти безвреден, дыра — это отказ функции), и только
потом резать. Позиционная обрезка — последнее средство, требует явного `--truncate` и
обязана называть границу. Без `--truncate` список, который не влез, выдаётся **целиком** с
`fits:false` и кодом возврата 1: пусть вызывающий решает, что хуже.

Отчёт пишется в отдельный файл, а сам список — в stdout. Не «оба в stdout»: отчёт,
попавший в файл списка, делает его невалидным для nft, и на живом роутере это стоило
исчезновения всей таблицы `inet steer`. Поэтому управляющий слой обязан ещё и проверять
результат перед подменой файла.

### Чем сливать: склейка по плотности, а не по разрывам

Измерено на реальном списке блокировок РФ (28 559 префиксов после агрегации, 19 122 в
обрезанном виде на 4C):

| приём | элементов | покрытие |
|---|---|---|
| без агрегации | 19 122 | до `198.38.96.0`, выше дыра |
| мостование разрывов (slack 256) | 13 155 | то же |
| slack 1024 / 4096 | 17 125 / **20 801** | *хуже*, чем без агрегации |
| **склейка /24 при ≥2 адресах** | **10 716** | **весь список целиком** |

Три вывода, каждый оплачен измерением:

1. **Мостование разрывов упирается в ~12 000 префиксов** и ниже не идёт, сколько slack ни
   давай. При ~1,3 КБ памяти на префикс это всё равно не влезает в 13–15 МБ.
2. **Широкий slack работает против себя.** Когда расширение задевает адрес из списка
   исключений, диапазон приходится резать на фрагменты вокруг него — и результат
   становится больше, чем вообще без агрегации. Лестница обязана останавливаться на
   минимуме, а не «идти до упора».
3. **Склейка по плотности — другой рычаг, и она сильнее.** Полный список после неё
   занимает меньше, чем обрезанный занимает сегодня: дыра убирается с экономией памяти
   вдвое, ценой ~580 тысяч лишних адресов (0,013% IPv4), которые поедут в туннель.

Порог именно **≥2**: в этом списке 8 428 из 10 716 сетей /24 содержат ровно один адрес,
и склеивать такую /24 — 255 лишних адресов при экономии в ноль элементов.

Исключения проверяются **по кандидату**: если в склеиваемой /24 есть адрес, который
обязан идти напрямую, эта /24 не склеивается и остаётся своими /32. Это дёшево, в отличие
от проверки при мостовании, которая и приводит к крошению из пункта 2.

Агрессивность склейки — свойство **выхода**, а не глобальная настройка: лишний адрес
безвреден, когда канал ведёт в туннель, и вреден, когда канал ведёт `direct` (тогда
лишний адрес теряет туннель). Движок обязан знать это из `outputs[].kind`, а не спрашивать.

## 3. Глаголы

Общий флаг у всех: `--spec FILE` (по умолчанию `/etc/steer/spec.json`).

| команда | что делает |
|---|---|
| `steer apply [--dry-run]` | компилирует спеку; `--dry-run` печатает правила, ничего не меняя |
| `steer status` | применённое + наблюдаемое, схема выше |
| `steer explain ADDRESS` | в какую группу попадёт адрес, каким выходом уйдёт, через какой девайс |
| `steer dnsd` | резолвер для доменных каналов; читает ту же спеку |
| `steer failover [-v]` | один проход: выбрать живое устройство по каждому выходу |
| `steer fit --budget N [IN]` | подогнать список префиксов под память |
| `steer vless OUTPUT` | поднять TUN выхода `kind=vless` (только `steer-extended`) |
| `steer outputs [--kind K]` | перечислить выходы |
| `steer needs-dnsd` | код 0, если в спеке есть доменные каналы |
| `steer verify` | *не реализовано:* совпадает ли живое состояние ядра с применённым |

`apply` — компилятор, `status` — опрос по требованию, шины нет. Долго живут только `dnsd`
(и только когда в спеке есть доменный канал: без него не запускается резолвер и не
генерируется редирект, который на него смотрит) и процессы `vless`. `failover` — тоже один
проход по вызову: «раз в минуту» — дело того, кто вызывает, и таймер ставит init-скрипт.

**Проба failover не трогает живой путь.** Пинг уходит через отдельную таблицу с правилом по
адресу источника кандидата — иначе, чтобы проверить запасной туннель, пришлось бы сначала
переключиться на него, то есть уронить работающий ради вопроса «работает ли другой». Целей
две (`1.1.1.1` и `8.8.8.8`), потому что одна может быть заблокирована именно в этом
туннеле, и тогда здоровый путь выглядел бы мёртвым.

**Залипший туннель оживляется `ifdown` + `ifup`, а не `ifup`.** В netifd `ifup` на уже
поднятом интерфейсе — no-op, поэтому залипший туннель сам не оживёт никогда. Есть выдержка
в 300 секунд: перезапуск интерфейса — заметное действие, и делать его каждую минуту хуже,
чем не делать вовсе.

`outputs` и `needs-dnsd` существуют, чтобы вызывающий **спрашивал движок**, а не искал
ключи в JSON. Init-скрипт искал `"domains_file"`; спека получила множественное
`domains_files`, совпадение молча перестало срабатывать — резолвер не запускался, а редирект
DNS `apply` всё равно ставил, и DNS на роутере умирал целиком без единой строчки в логе.
Движок — единственное, что знает, что он сгенерирует.

Всё это один бинарник. Компилятор и резолвер читают одну спеку одним парсером, поэтому
расхождение между «какие наборы создал компилятор» и «в какие пишет резолвер»
невыразимо — а именно на таком расхождении в splify 1 ломались доменные функции. Фиттер —
подкомандой по той же причине: раздельная поставка означала бы роутер, где движок есть, а
подогнать список нечем, то есть ровно тот случай, для которого фиттер и написан.

## 4. Чего в схеме 1 нет

Названо, чтобы не выглядело забытым: маршрутизация IPv6 (шов есть, реализации нет —
AAAA для совпавших доменов глушится, чтобы клиент не ушёл в обход по IPv6),
преобразующие выходы (обход DPI — только заявлены), ограничение по времени и скорости,
per-MAC селекторы (`from` принимает подсети и адреса), `steer verify`, транспорты
gRPC и xhttp для `kind: vless`.

Отдельно, чтобы не было лишних ожиданий: `"family"` в спеке — это **место** для будущего
IPv6, а не поле, которое движок читает. Сейчас парсер его не знает, всё компилируется как
IPv4, и указывать `"family": "ipv6"` бессмысленно: отказа не будет, эффекта тоже.
А `traceroute_hops` работает только на выходе без NAT — выше сказано, почему при
masquerade иначе нельзя.
