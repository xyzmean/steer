# Контракт steer, схема 1

Всё, что пересекает шов между управляющей программой (splify) и движком. Формат —
**JSON**: он уже разбирается всем, что есть в базовом OpenWrt (`jsonfilter`, blobmsg),
LuCI говорит на нём нативно, и массивы сохраняют порядок — а порядок каналов у нас
семантически значим.

YAML сознательно не берётся: парсера в базовой системе нет (это ~100 КБ overlay на
коробке, где их шесть), а его неоднозначность (`no` → false, `1.10` → число) для
конфига, из которого генерируются правила фаервола, превращает опечатку в тихо другое
поведение. Для тех, кто правит конфиг руками, предполагается `steer convert cfg.yaml`
на большой машине — но на роутер попадает JSON.

## 1. Спецификация (вход)

```json
{
  "schema": 1,
  "from_default": ["192.168.1.0/24"],
  "outputs": {
    "vpn":    { "kind": "interface", "device": "warp0" },
    "geo":    { "kind": "interface", "device": "debug" },
    "direct": { "kind": "direct" }
  },
  "channels": [
    { "name": "geoblock", "match": { "domains_file": "/etc/steer/lists/geo.lst" },  "out": "geo" },
    { "name": "blocked",  "match": { "prefixes_file": "/etc/steer/lists/ipsum.lst" }, "out": "vpn" },
    { "name": "tv",       "from": ["192.168.1.50"], "match": { "any": true },       "out": "vpn" }
  ]
}
```

### Инварианты

1. **Порядок каналов — это приоритет.** Первое совпадение выигрывает. Генератор ставит
   правила в этом же порядке и защищает их проверкой «метка ещё не стоит», чтобы
   следующий канал не переразметил пакет.
2. **`match` содержит только пути к файлам.** Никаких встроенных списков — см. правило
   про слабое железо в README. Файл читает движок, напрямую в набор.
3. **Выход именованный, девайс подменяемый.** `outputs.vpn.device` меняется управляющей
   программой (это failover), и каналы при этом не трогаются. Смена девайса не должна
   требовать пересборки правил — только перепривязки таблицы.
4. **Метки и таблицы движок распределяет сам** и хранит в постоянном реестре: спека их
   никогда не называет. Реестр обязателен — иначе после перезагрузки метки
   перетасуются, а рядом живут mwan3 и fw4 со своими.
5. **Семейство — свойство канала**, `"family": "ipv4"` по умолчанию. `ipv6` пока не
   реализован, но шов есть: иначе поддержка v6 станет переписыванием, а не доработкой.
6. **Незнакомая `schema` — отказ, а не догадка.** Мажор ломает совместимость явно.
7. **Каждое сгенерированное правило несёт имя канала** в комментарии nft. Без этого
   невозможны ни `explain`, ни счётчики по каналам, а отладка на роутере без
   инструментов становится дороже самой поломки.

## 2. Состояние (выход)

`steer status --json`:

```json
{
  "schema": 1,
  "generation": 42,
  "applied_at": 1754870400,
  "outputs": {
    "vpn": { "kind": "interface", "device": "warp0", "up": true, "table": 200, "mark": "0x40000" },
    "geo": { "kind": "interface", "device": "debug", "up": true, "table": 202, "mark": "0x80000" }
  },
  "channels": [
    { "name": "geoblock", "out": "geo", "elements": 465,  "packets": 5009, "bytes": 1799237 },
    { "name": "blocked",  "out": "vpn", "elements": 9872, "packets": 4,    "bytes": 418 }
  ],
  "warnings": [
    { "code": "list_truncated", "channel": "blocked", "kept": 19122, "source": 30726,
      "covered_through": "198.38.96.0",
      "text": "не хватило памяти: защита действует до 198.38.96.0, выше адреса идут как без steer" }
  ]
}
```

`covered_through` — обязательное поле такого предупреждения. Сообщать «оставлено 19 122
из 30 726» бесполезно: пользователь видит, что часть сайтов работает, а часть нет, и не
может связать это с памятью. Пример из жизни: у youtube.com десятки A-записей, и на
обрезанном списке `142.250.130.190` уходил в туннель, а `216.58.198.206` — напрямую,
потому что отсечка легла на `198.38`. Симптом выглядел как «пару часов назад работало».

**Отсюда требование к фиттеру:** при нехватке памяти сначала агрессивнее сливать
префиксы, сохраняя полное покрытие (лишний адрес в туннеле почти безвреден, дыра — это
отказ функции), и только потом резать. Позиционная обрезка — последнее средство, и она
обязана называть границу.

### Чем сливать: склейка по плотности, а не по разрывам

Измерено на реальном списке блокировок РФ (28 559 префиксов после агрегации, 19 122 в
обрезанном виде на 4C):

| приём | элементов | покрытие |
|---|---|---|
| без агрегации | 19 122 | до `198.38.96.0`, выше дыра |
| мостование разрывов (slack 256) | 13 155 | то же |
| slack 1024 / 4096 | 17 125 / **20 801** | *хуже*, чем без агрегации |
| **склейка /24 при ≥2 адресах** | **10 716** | **весь список целиком** |

Три вывода, каждый оплачен измерением:

1. **Мостование разрывов упирается в ~12 000 префиксов** и ниже не идёт, сколько slack ни
   давай. При ~1,3 КБ памяти на префикс это всё равно не влезает в 13–15 МБ.
2. **Широкий slack работает против себя.** Когда расширение задевает адрес из списка
   исключений, диапазон приходится резать на фрагменты вокруг него — и результат
   становится больше, чем вообще без агрегации. Лестница обязана останавливаться на
   минимуме, а не «идти до упора».
3. **Склейка по плотности — другой рычаг, и она сильнее.** Полный список после неё
   занимает меньше, чем обрезанный занимает сегодня: дыра убирается с экономией памяти
   вдвое, ценой ~580 тысяч лишних адресов (0,013% IPv4), которые поедут в туннель.

Порог именно **≥2**: в этом списке 8 428 из 10 716 сетей /24 содержат ровно один адрес,
и склеивать такую /24 — 255 лишних адресов при экономии в ноль элементов.

Исключения проверяются **по кандидату**: если в склеиваемой /24 есть адрес, который
обязан идти напрямую, эта /24 не склеивается и остаётся своими /32. Это дёшево, в отличие
от проверки при мостовании, которая и приводит к крошению из пункта 2.

Агрессивность склейки — свойство **выхода**, а не глобальная настройка: лишний адрес
безвреден, когда канал ведёт в туннель, и вреден, когда канал ведёт `direct` (тогда
лишний адрес теряет туннель). Движок обязан знать это из `outputs[].kind`, а не спрашивать.

## 3. Глаголы

| команда | что делает |
|---|---|
| `steer apply [--spec F] [--dry-run]` | компилирует спеку; `--dry-run` печатает правила, ничего не меняя |
| `steer status --json` | применённое + наблюдаемое, схема выше |
| `steer explain <ip\|домен>` | в какой канал попадёт, каким выходом уйдёт, через какой девайс |
| `steer verify` | совпадает ли живое состояние ядра с последним применённым |

Демона нет: `apply` — компилятор, `status` — опрос по требованию. Понадобятся события —
у DNS-части есть свой лог; шину строить незачем.

## 4. Чего в схеме 1 нет

Названо, чтобы не выглядело забытым: IPv6 (шов есть, реализации нет), преобразующие
выходы (обход DPI — только заявлены), ограничение по времени и по скорости, per-MAC
селекторы (`from` пока принимает подсети и адреса).
