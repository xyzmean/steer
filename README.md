# steer

Движок маршрутизации трафика по политикам для OpenWrt.

На входе — декларативная спецификация: какие потоки трафика существуют и куда каждый
должен уходить. На выходе — правила nftables, таблицы маршрутизации и наборы адресов,
установленные атомарно. Больше steer ничего не делает: он не решает, какой туннель
сейчас хороший, не качает списки, не рисует интерфейс и не имеет мнения о том, зачем
вам понадобилось направлять трафик.

Мнение — дело сборки поверх движка. [splify](https://github.com/xyzmean/splify) —
такая сборка: готовые списки блокировок, автонастройка туннеля, failover, веб-интерфейс.

## Модель: канал

Единица конфигурации — **канал**: `(кто, что) → выход`.

```
клиенты 192.168.1.0/24  +  домены из geo.lst    →  выход "geo"    (девайс debug)
клиенты 192.168.1.0/24  +  префиксы из ipsum.lst →  выход "vpn"    (девайс warp0)
всё остальное                                    →  напрямую
```

«Кто» — это подсети, MAC-адреса или входные интерфейсы. Именно оно даёт «гнать в туннель
только телевизор» или «этот VLAN мимо всего», и именно его обычно забывают заложить.

Каналы **упорядочены, первое совпадение выигрывает** — порядок виден в конфиге, а не в
порядке генерации правил.

## Выходы бывают двух разных родов

Это не деталь реализации, а то, что определяет, куда правило попадёт в цепочке:

- **перенаправляющие** меняют *куда* идёт пакет — таблица маршрутизации, правило, NAT;
- **преобразующие** маршрут не меняют, а меняют *как* пакет выглядит на том же пути
  (обход DPI и подобное).

Они композируемы: «через туннель, и по пути ломать DPI» — осмысленная конфигурация.
Плюс два вырожденных выхода: `direct` (явно мимо всех каналов) и `block`.

## Слабое железо — требование, а не пожелание

Целевая коробка — Mi Router 4C: mipsel, одно ядро 580 МГц, 13–15 МБ свободной памяти,
6 МБ overlay. Отсюда жёсткие правила, каждое из которых уже оплачено чужой болью:

- **спецификация не содержит содержимого списков** — только пути к файлам. Иначе за
  19 тысяч префиксов платишь парсингом JSON и держишь их в памяти дважды;
- **элементы наборов заливаются через netlink**, а не вызовом `nft` на каждый элемент;
- **никакого второго демона**: состояние отдаётся по запросу, шины нет;
- **измерения фиксируются**: потолок префиксов, время применения, RSS. Обещание «работает
  на слабом железе» держится цифрами, а не намерением.

Замеренное на 4C для калибровки: загрузка набора стоит ~1,3 КБ памяти на префикс, полный
цикл обновления списков на shell+awk занимает 6–8 минут (это и есть главная причина
перевести обработку списков в компилируемый код).

## Состояние

Два разных ответа, которые нельзя смешивать:

- **применённое** — какая спека живая, когда применена, какой выход к какому девайсу
  привязан, реестр меток и таблиц;
- **наблюдаемое** — счётчики по каналам, здоровье выходов, размеры наборов, последняя ошибка.

Плюс `steer explain <ip|домен>` — «в какой канал попадёт и куда уйдёт». Это единственный
ответ, который нельзя получить, глядя на голый nft, и он работает только потому, что
каждое сгенерированное правило несёт имя своего канала.

Контракт: [docs/contract-v1.md](docs/contract-v1.md).

## Состояние проекта

Работает на железе — Mi Router 4C (mipsel, одно ядро, ~13 МБ свободно) и filogic.
Есть: IP-каналы, доменные каналы с fake-IP, несколько туннельных выходов
одновременно, реестр меток на диске, `apply/status/explain/dnsd`, init-скрипт,
пакеты apk на шесть архитектур, 35 офлайн-тестов.

Нет: `verify`, маршрутизации IPv6, преобразующих выходов (обход DPI), селекторов
по MAC. Слой списков — выбор категорий, загрузка, расписание — сознательно снаружи:
это дело сборки поверх движка.

```sh
make test                 # 35 тестов, без роутера и без сети
./build.sh                # статические бинарники + пакеты apk
steer apply --dry-run     # посмотреть правила, ничего не меняя
steer explain 216.58.198.206
```
